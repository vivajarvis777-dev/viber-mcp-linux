# Контрольний вхід Viber: доповнення до аудиту, 2026-10-27

## Поточний висновок

Фаза 1 не пройдена. Доставка контрольного повідомлення та номер співрозмовника
підтверджені. Стабільний ID повідомлення і доказовий зв'язок
Notify → конкретне вхідне повідомлення → перевірений чат не встановлені.

Цей документ замінює попередні висновки «контрольного входу ще не було» та
«номер відправника не підтверджений». Старі звіти залишені як історія.
Це звіт про виконані перевірки, а не production adapter.

## Чому observer повернув false

У зафіксованому Notify body мало тип dbus.String. Історична функція
marker_in шукає точну безперервну підпослідовність лише в body.
Окрема offline перевірка, витягнута через AST без імпорту runtime:
plain String=true; HTML навколо цілого маркера=true;
HTML усередині маркера=false; Array=true; Struct=true; Dictionary=false.

Отже, body того Notify не містило безперервного exact marker.
Словники функція не обходить, але це НЕ пояснює false для фактичного
body типу String. Перетворений/прихований/скорочений текст або інша подія —
можливі пояснення, не доведені причини. Початковий payload не збережений,
тому історичну причину точніше з цих даних встановити неможливо.

D-Bus sender тут — з'єднання ПРОЦЕСУ Viber, не клієнтський акаунт.
summary_matches_test_phone=false не доводить неправильного клієнта:
summary не є незалежним джерелом його номера.

## Порівняння доступних джерел

| Джерело | Що доведено | Межа |
| --- | --- | --- |
| GUI | Маркер і вхідна бульбашка | Не дає перевіреного стабільного message ID |
| Native Copy number | Точний номер відкритого співрозмовника | Не пов'язує минулий Notify з цією бульбашкою; не дає внутрішнього chat ID |
| Notify | Подія від процесу Viber | Немає доведеного mapping на конкретне повідомлення/чат |
| AT-SPI | Доступне дерево й події | Прочитані Name/Text/Attributes не дали потрібних значень |
| read_open_chat | Тексти; recipient може походити з current_phone | Кеш не є identity; немає перевірених direction/message ID |
| OCR | Візуальне читання | Текст/час/позиція не замінюють стабільного ID |
| viber.db | Звичайний read-only SQLite повернув file is not a database | Причина не доведена; декодування/ключі не досліджувалися |
| Tray/Launcher/File events | Зміна загального стану | Не доказ нового конкретного incoming message |

## Межі та стан

Новий workflow, webhook, adapter, durable inbox і ліміт п'ять відповідей
не створено. Заготовка auto responder не запускалася; автовідповіді вимкнені.
Немає нового повідомлення клієнтам, production patch, рестарту, зміни IBAN,
вихідної черги, Telegram чи fallback. GUI відкривав існуючий контрольний чат,
картку та меню; читання могло змінити статус прочитання. Не стверджувати,
що UI лишився зовсім незмінним. Активні діагностичні спостереження завершено.

Скриншоти, попередній буфер, клієнтський текст, runtime logs і секрети
не включені в Git. Цей звіт реконструйовано з результатів інструментів
і локальних матеріалів; він не є збереженим raw Notify capture.

Попередній live/source drift збережено: release HEAD b4631ff,
змінений viber_mcp_service.py та локальні recipient_identity.py,
pre_dispatch_recovery.py, repair-backups/. Чиста база MCP аудиту c8df58b.
Не переносити audit checkout поверх release.

## Наступний крок

Antigravity має знайти або обґрунтовано відхилити придатне джерело зв'язку
message ID + chat/sender identity + incoming direction + event.
Почати зі source-level аналізу вже написаного MCP, без повторного тесту
та без активації існуючої заготовки. Покращення діагностики Notify саме
по собі не є вирішенням цієї задачі.

Критерії майбутнього приймання: повтор однієї події зберігає ID;
два окремі однакові тексти мають різні ID; однакові імена, групи,
власні/технічні події не авторизують відповідь. Відкритий/згорнутий чат,
вимкнені сповіщення, burst та рестарт ще не прийняті.
Нові контрольні входи або зміни стану production потребують конкретного
погодженого плану; цей snapshot не є дозволом на їх виконання.
