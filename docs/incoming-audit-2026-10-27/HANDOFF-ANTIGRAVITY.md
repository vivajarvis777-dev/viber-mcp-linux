# Handoff для Antigravity: подієвий автовідповідач Viva!Gas

Дата: 2026-10-27, Europe/Kiev. Передача від Codex за прямим дорученням власника.
Antigravity — агент, який раніше розробляв MCP для цього Viber.

## Мета власника

Окремий подієвий автовідповідач на нові особисті вхідні повідомлення клієнтів
у Viber. Бізнес-логіка — в окремому n8n workflow, надсилання через native n8n
MCP Client і наявний MCP. Без polling чатів і без паралельного Python sender.
Зберегти чинну IBAN-платіжну схему, вихідну чергу, Telegram та fallback.

Власник уточнив:
- єдиний публічний контакт: **Павло, Viva!Gas — 067 238 2080**;
- відповідати на кожне нове повідомлення, але максимум **п'ять відповідей на чат**,
  щоб не утворювався нескінченний обмін між ботами;
- період скидання ліміту не визначений. Робоче припущення — довговічний
  сукупний ліміт без автоматичного скидання; це не додаткова погоджена вимога;
- повтор тієї самої події не є новим клієнтським повідомленням;
- лише відповідний особистий чат із підтвердженою попередньою IBAN-доставкою
  може пройти майбутній gate відповіді.

Початкове попередження про автоматичний канал — окремий кандидат зміни
майбутнього початкового повідомлення. Чинні шаблони не змінені.

## Точний стан і точка зупинки

**Фаза 1 — частково виконана, BLOCKED. Фази 2–3 не розпочато.**

Доведено доставку контрольного повідомлення, вхідний напрямок у GUI та точний
номер співрозмовника через native Copy number. НЕ доведено зв'язок
зафіксованого Notify із цим конкретним повідомленням; немає перевіреного
сталого message ID та внутрішнього chat ID.

Завдання Antigravity — закрити саме цю технічну прогалину або надати
доказову відповідь, що доступні інтерфейси її не закривають.
Не починати з повторної перевірки доставки чи номера: вони вже підтверджені.

Немає створеного нового workflow, adapter, webhook, durable inbox,
ліміту п'яти відповідей, outgoing canary чи активації.
Усі наші спостерігачі завершено. Після handoff Codex не веде паралельної
фонової роботи; сама публікація цього файла не запускає Antigravity.

## Підтверджені факти

- Exact marker: VIVAGAS-IN-20261027-02. Власник уже надіслав його й підтвердив
  надсилання. Пізніше повторне «Надіслав» у чаті — підтвердження того тесту,
  а не підстава вимагати ще одне повідомлення.
- Пасивне вікно ~420.39 с: 1 Notify від PID Viber, 1 контрольний ListNames,
  14 AT-SPI PropertyChange, 1 LauncherEntry.Update.
- У Notify body типу String exact marker не знайдено; summary не збіглося
  з очікуваним номером. Body, summary і значення hints не зберігали.
- GUI: exact marker у білій вхідній бульбашці контрольного чату.
- Native Copy number: рівно один видимий пункт; отриманий номер точно
  відповідає очікуваному тестовому номеру. Буфер відновлено, composer незмінний,
  повідомлень не надсилали. Повні тестові номери є в чаті власника, не в Git.
- AT-SPI після відкриття чату: 95 вузлів, 5 Text, 0 помилок,
  без обрізання. Прочитані Name/Text не містили маркера чи номера,
  GetAttributes порожні. EditableText відсутній; composer читався через Text
  з перевіркою видимої геометрії.
- Notify підтверджує процес Viber, а не ідентичність клієнта.
  Збіг часу з GUI не доводить correlation.
- Exact String matcher працює на offline прикладах.
  Пропуск Dictionary та HTML усередині маркера відтворені, але не доведені
  як причина саме цього Notify. Raw payload немає — не вигадувати його.
- read_open_chat може повертати current_phone з кешу. Це не identity.
  Наявні результати текстового читання не містять перевіреного ID/напрямку.
- Tray/launcher/file-change події не визначають конкретне incoming message.
- Звичайне SQLite read-only читання viber.db дало file is not a database.
  Шифрування не оголошувалося доведеним, ключі/декодування не досліджувалися.

## Перший робочий етап Antigravity

1. Прочитати актуальні snapshots та source MCP, звірити baseline/drift.
2. Знайти конкретний доступний інтерфейс, що надає stable message ID,
   чат/відправника й incoming direction, та доказове зіставлення з подією.
   Для кожного кандидата описати контракт і походження полів.
3. Якщо проблема в observer — підготувати ізольований reviewable fix
   і offline перевірки. Діагностичний patch не дорівнює робочому adapter.
   Не відновлювати raw payload припущеннями.
4. Якщо потрібен новий live-тест, зміна notification settings, рестарт
   або інший доступ — спочатку надати точну пропозицію, причину і межі.
   Новий тест, виробничі зміни та надсилання цим handoff не дозволені.
5. Завершити етап конкретним доказом або конкретним блокером, без заяв
   «продовжую» при фактичній зупинці. Відображати результати у Git.

Зараз дозволені source-level/read-only дослідження й ізольовані offline
перевірки. Копіювання контактного номера вже було окремо виконане.
Не розширювати доступ, не створювати чат, не надсилати повідомлення,
не змінювати production/workflow/IBAN та не перезапускати сервіси.

## Критерії завершення Фази 1

- Незалежний доказ особистого чату, відправника й incoming direction.
- Конкретний event однозначно пов'язаний із конкретним повідомленням.
- Повтор однієї події має той самий ID; два різні повідомлення
  з однаковим текстом мають різні ID.
- Однакові display names, групи, власні/технічні повідомлення не проходять.
- Після окремого погодження перевірено відкритий/згорнутий чат,
  вимкнені сповіщення, burst та рестарт. Зараз ця матриця не пройдена.
- Немає polling чатів. Якщо обраний механізм не забезпечує вимоги,
  це явно зафіксовано замість послаблення контракту.

## Лише після проходження Фази 1

Фаза 2: ізольований вимкнений n8n workflow та event adapter,
автентифікована передача, durable inbox/ack і дедуплікація,
перевірка попередньої IBAN-доставки, атомарний ліміт п'ять відповідей.
Невизначений send не повторювати автоматично; його слот резервувати до звірки.

Фаза 3: синтетичні перевірки duplicate/burst/restart/n8n-down/Viber-busy/
unknown-send, export, runbook, Git diff. Production activation і outgoing
canary — тільки за конкретним окремим погодженням згідно
[runbook проєкту](https://github.com/vivajarvis777-dev/vivagas-iban-viber/blob/audit/viber-incoming-20261027/docs/runbook.md).

Не вмикати чинний viber_auto_responder.py як швидке рішення:
resolver допускає first-match імен/підрядків і числових заголовків;
обробник не доводить ID/напрямок/особистий чат;
Python sender обходить потрібну n8n-логіку; webhook fire-and-forget
не забезпечує погоджений контракт. Ці недоліки описані в початковому аудиті.
