# Лише збережені контакти: оцінка здійсненності

Вимога Господаря від2026-10-18: повідомлення тільки контактам, збереженим в
адресній книзі; нові контакти виключити. Бажано прибрати Copy number із pipeline,
якщо адресата можна надійно встановити іншим способом.

## Підтверджено

- `Service.list_contacts` читає `VIBER_CONTACTS_FILE`: ручний dict alias→phone.
  `resolve` приймає також raw phone. Це не Viber address book і не доказ saved status.
- `search_and_open` перевіряє однозначність назви/номера, а не членство в книзі.
  Історія чату та ім'я у header не є stable contact/chat binding.
- AT-SPI worker використовує калібрований phone/self marker; спеціальний reader
  підтверджує Text composer. Жоден із них не має перевіреного saved-contact ID.
- На вже доступних локальних файлах переглянуто лише16-байтові сигнатури та
  схеми SQLite, без значень акаунта/секретів/повідомлень/контактів.
  `config.db`: Accounts, UserSettings, CommonSettings; `data.db`: DataTable
  (Key, Category, Value). Це не встановлює контракту saved membership чи chat binding.
- Третя .db не має SQLite header. Це не доводить шифрування; формат/схему не
  підтверджено, дешифрування або доступ до ключів не виконувалися.

## Межа висновку

У коді та перевіреній схемі немає доведеного provider saved-contactID→chat.
Це не доказ, що дані відсутні взагалі: generic key/value store або UI можуть
мати додаткові дані, але їхній зміст/семантика ще не досліджені. Не створено
штучного adapter, whitelist під виглядом address book або нової bypass option.
Production лишається read-only, нових live UI/input probes не було.

Навіть усунення clipboard identity не усуває clipboard paste у поточному
`X11Backend.write`. Ці два використання потрібно оцінювати окремо.

## Наступний мінімальний крок

Окремо погоджений огляд адресної книги у Viber: без запису тексту, додавання
контактів чи send. Потрібно встановити:1)що список саме saved contacts;
2)який стабільний ключ відрізняє однойменні записи;3)як незалежно підтвердити,
що відкрита розмова відповідає вибраному ключу;4)як перевірити зміни між вибором
і записом. Не приймати merely selected row/current chat/name за незалежний proof.
До цього read-only дослідження нова live-згода не отримана. Попередній STRICT-01
спожитий і не поширюється на новий огляд чи відправлення.

Якщо ці ознаки реально доступні, можна підготувати мінімальний adapter, прив'язати
всі write operations до contact/chat key та прибрати Copy number. Якщо ні —
чітко повідомити блокер, не зменшувати точність перевірки адресата.
